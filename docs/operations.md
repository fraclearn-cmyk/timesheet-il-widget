# Эксплуатация сервиса табеля

Документ описывает безопасный запуск текущей версии для 40 изолированных аккаунтов amoCRM. Все команды выполняются из корня репозитория. Значения секретов ниже являются именами переменных, а не готовыми паролями.

## Требования и подготовка

- Docker Engine с Compose v2 либо Python 3.12 и PostgreSQL 15 для запуска без контейнеров.
- Публичный HTTPS-адрес backend для webhook и OAuth redirect.
- Отдельные сильные значения `POSTGRES_PASSWORD`, `AMOCRM_CLIENT_SECRET` и `SECRET_KEY` длиной не менее 32 символов.
- Резервная копия базы перед обновлением приложения или схемы.

Скопируйте `backend/.env.example` в локальный `.env`, заполните обязательные значения и не добавляйте этот файл в Git. `DATABASE_URL` внутри Compose должен указывать на сервис `db`, например `postgresql://timesheet:<пароль>@db/timesheet`. База наружу не публикуется.

## Чистый запуск и обновление

Проверьте итоговую конфигурацию, не выводя секреты в журнал общего доступа:

```bash
docker compose --env-file .env config --quiet
docker compose --env-file .env build backend
docker compose --env-file .env up -d
docker compose --env-file .env ps
```

Entrypoint backend выполняет `python -m alembic upgrade head` до запуска Uvicorn. При ошибке миграции API не стартует. Для ручного контроля:

```bash
docker compose --env-file .env exec backend python -m alembic heads
docker compose --env-file .env exec backend python -m alembic current
```

Обе команды должны показывать единственную голову `014`. Несколько голов или версия базы ниже `014` запрещают принимать трафик. Не запускайте несколько экземпляров, которые одновременно накатывают новую миграцию; сначала обновите схему одной release-задачей. Перед увеличением числа экземпляров API настройте общий лимит запросов на доверенном ingress/API gateway, как описано ниже.

## Проверки состояния

- `GET /health` — liveness процесса. Ответ `200` означает, что процесс работает; база при этом может быть недоступна.
- `GET /health/ready` — readiness. Ответ `200` означает доступную PostgreSQL и схему на единственной актуальной голове. `503` означает, что экземпляр нельзя включать в балансировщик.

Compose использует readiness backend и `pg_isready` для PostgreSQL. После запуска дождитесь статуса `healthy`, затем отдельно вызовите оба адреса через ваш HTTPS ingress.

## Резервное копирование и восстановление

Создавайте ежедневный custom-format backup и храните копии вне сервера приложения:

```bash
docker compose --env-file .env exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > timesheet.dump
```

Перед восстановлением остановите backend, чтобы новые записи не попали между backup и restore. Восстанавливайте в новую пустую базу PostgreSQL 15, а не поверх работающей:

```bash
docker compose --env-file .env stop backend
docker compose --env-file .env exec -T db sh -c 'createdb -U "$POSTGRES_USER" timesheet_restore'
docker compose --env-file .env exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d timesheet_restore' < timesheet.dump
```

Подключите тестовый backend к восстановленной базе, выполните `alembic current`, `/health/ready` и выборочную сверку аккаунтов/табеля. Только после этого переключайте production `DATABASE_URL`. Регулярно проверяйте восстановление на отдельной базе: наличие файла backup само по себе не доказывает, что он пригоден.

## Расчёт на 40 аккаунтов

Для 40 аккаунтов оставьте `INGESTION_MAX_CONCURRENT_ACCOUNTS=8`: worker обрабатывает готовые аккаунты справедливыми волнами, а lease в PostgreSQL предотвращает параллельную обработку одного аккаунта. Начальные ориентиры для одного экземпляра backend: 2 CPU, 2–4 ГиБ RAM и PostgreSQL с 2 CPU, 4 ГиБ RAM и SSD. Это стартовая конфигурация, а не гарантия нагрузки; меняйте её по метрикам реальных пользователей.

Следите за временем ответа `/api/v1/team/status`, числом `429`, задержкой ingestion, размером очереди готовых аккаунтов, ошибками OAuth и использованием соединений PostgreSQL. Локальный проверочный контракт для status — p95 менее 250 мс на подготовленном наборе из 40 аккаунтов после прогрева. Он подтверждает отсутствие линейного роста SQL-запросов, но не заменяет замер production через HTTPS.

## Журналы, ошибки и request ID

Backend пишет структурированные JSON-журналы. Каждый ответ содержит `X-Request-Id`; безопасные API-ошибки также возвращают то же значение в `error.request_id`. Для поиска сбоя возьмите этот ID из ответа и найдите событие в централизованном журнале. Не записывайте access/refresh token, authorization code, cookie, webhook URL/key, пароли, полные заголовки авторизации или сырые webhook payload.

Внешний ingress должен сохранить входящий `X-Request-Id` только если он соответствует серверному формату; приложение само заменяет неверное значение. Стандартный access log Uvicorn отключён, чтобы URL с секретным webhook path не попал в журнал.

## Лимиты и восстановление после сбоев

- Авторизованные запросы ограничиваются отдельно по проверенному account/user; общий NAT не объединяет 40 клиентов в одну завершённую квоту.
- До дорогой авторизации допускается не более 64 одновременных запросов с одного сетевого адреса.
- Публичные и неизвестные маршруты имеют отдельный ограниченный bucket.
- Webhook принимает не более 64 КиБ и 10 запросов в минуту на callback; `Retry-After` указывает паузу при `429`.
- Клиентский polling использует ограниченный backoff до 300 секунд и не создаёт ложный статус «Работает» при недоступном backend.

Встроенные buckets и ограничение одновременной авторизации хранятся в памяти одного Python worker. При нескольких workers или экземплярах они не являются общей квотой: эффективный предел умножается, а вытеснение старых buckets происходит независимо. Для cluster-wide защиты настройте shared rate/concurrency limit на доверенном ingress/API gateway. Ключи авторизованной квоты должны сохранять разделение проверенных account/user, чтобы 40 аккаунтов за одним NAT не блокировали друг друга; до авторизации сетевой адрес можно использовать только для общего ограничения одновременной дорогой работы.

При временном сбое amoCRM или HTTP `429/5xx` worker сохраняет подтверждённый checkpoint, повторяет запрос с ограниченным backoff и не перескакивает через необработанную страницу. После перезапуска другой worker может забрать истёкший lease. Повторная доставка подавляется account-scoped dedup ключом. При длительном сбое сначала восстановите PostgreSQL и readiness, затем OAuth-доступ, после чего наблюдайте успешное продолжение с последнего checkpoint; не сдвигайте watermark вручную.

## CI и внешние проверки выпуска

Workflow `.github/workflows/ci.yml` поднимает PostgreSQL 15, накатывает Alembic, проверяет единственную голову `014`, запускает полный backend, Node, Playwright и package/ZIP gates, Black, compileall, `git diff --check`, `docker compose config` и сборку backend image.

Перед production-выпуском требуются результаты реального CI runner и отдельный запуск `docker compose build/up` в целевой среде. Локальная машина без Docker подтверждает только статические тесты конфигурации. Проверки реального OAuth redirect, прав/ролей, областей виджета, event catalog/pagination/delivery и доступного источника звонков выполняются отдельным контролируемым live gate amoCRM по `docs/amocrm-integration-limits.md`; локальные mocks его не заменяют.
