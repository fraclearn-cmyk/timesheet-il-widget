# Дизайн фазы 3: настройки виджета amoCRM

Дата: 2026-09-19

## Цель

Администратор настраивает учёт рабочего времени непосредственно в окне
установленного виджета amoCRM. Интерфейс выглядит нативно для amoCRM, содержит
только вкладки «Пользователи» и «Настройки» и сохраняет обе вкладки одной
стандартной кнопкой amoCRM.

Успешный результат:

- рабочий `init` не показывает редактор настроек;
- настройки доступны только подтверждённому администратору текущего аккаунта;
- пользователи и отдельные группы учёта загружаются, проверяются и сохраняются
  без дублирования;
- повторное открытие восстанавливает сохранённое состояние;
- «Скрыть виджет» скрывает рабочий UI, но не отключает серверный учёт.

## Принятые решения

- Интерфейс встроен непосредственно в `advancedSettings`; iframe и отдельная
  admin-страница не используются.
- Внешний вид следует нативным элементам и плотности интерфейса amoCRM.
- Обе вкладки сохраняются одной стандартной кнопкой через callback `onSave`.
- Группы учёта независимы от подразделений/групп amoCRM. Группировка amoCRM в
  списке пользователей служит только для поиска и навигации.
- Существующая `frontend/admin.html` остаётся неподключённым прототипом. Фаза 3
  не расширяет её и не переносит вкладки подразделений или статистики.

## Архитектура виджета

`widget/script.js` разделяет четыре обязанности:

1. `init` запускает только рабочую часть виджета и не создаёт настройки.
2. `settings` сохраняет стандартное минимальное поведение установки amoCRM.
3. `advancedSettings` монтирует контейнер двух вкладок и загружает единый снимок
   данных с backend.
4. `onSave` собирает локальное состояние обеих вкладок, выполняет клиентскую
   проверку и отправляет один идемпотентный запрос сохранения.

Разметка, логика и стили настроек изолируются в:

- `frontend/settings/settings.html` — шаблон двух вкладок;
- `frontend/settings/settings.js` — состояние, отрисовка, валидация и сбор
  payload;
- `frontend/settings/settings.css` — нативное оформление amoCRM без глобальных
  селекторов, влияющих на основную страницу.

Виджет предоставляет модулю настроек только API URL, проверенный контекст
авторизации и callbacks загрузки/сохранения. Модуль не принимает account/user ID
из редактируемых полей.

## Данные вкладки «Пользователи»

Для каждого синхронизированного пользователя показываются:

- имя, аватар и email;
- исходное подразделение/группа amoCRM как визуальная группировка;
- поиск по имени и email;
- «Учитывать рабочее время» (`track_time`);
- «Скрыть виджет» (`hide_widget`);
- отдельная группа учёта.

Правила:

- включённому в учёт пользователю обязательна одна активная группа;
- один пользователь не может одновременно состоять в двух активных группах;
- `hide_widget` не меняет `track_time` и не удаляет серверные данные;
- отключение учёта закрывает только будущее участие, сохраняя историю;
- неактивные пользователи amoCRM отображаются как недоступные для нового
  назначения, но их история не удаляется.

## Данные вкладки «Настройки»

Общие поля аккаунта:

- телефон поддержки;
- разрешённые рабочие статусы;
- значение повторного запуска смены по умолчанию.

Редактор отдельных групп учёта содержит:

- название;
- активность группы;
- руководителя;
- часовой пояс IANA;
- начало и конец рабочего дня;
- разрешение повторного запуска смены.

Удаление занятой или исторической группы не выполняется. Администратор сначала
переназначает активных сотрудников, после чего группу можно деактивировать.
Исторические ссылки остаются целыми.

## Backend API и сохранение

Backend добавляет account-scoped endpoints для:

- получения единого settings snapshot;
- списка синхронизированных пользователей;
- получения и редактирования групп;
- атомарного сохранения полного снимка фазы 3.

Каждый endpoint использует verified `RequestContext` фазы 2. Читающие и
изменяющие настройки операции требуют текущего live admin evidence. Переданные
клиентом account ID и внутренние ID не являются источником полномочий.

Сохранение выполняется в одной транзакции:

1. нормализовать payload и отклонить неизвестные/повторяющиеся ID;
2. проверить права, пользователей, руководителей, часовые пояса и расписание;
3. проверить одно активное членство и наличие группы у каждого tracked user;
4. применить upsert настроек, групп и memberships;
5. зафиксировать транзакцию только после успешной проверки всего снимка.

Повторная отправка того же снимка не создаёт новые группы или memberships.
Конфликт возвращает структурированный `409`; ошибки полей содержат стабильный
код и путь поля для подсветки интерфейсом.

## Загрузка и восстановление

При открытии `advancedSettings` UI показывает состояние загрузки, затем заменяет
локальное состояние единым серверным snapshot. Серверные ID сохраняются отдельно
от временных клиентских ключей новых групп.

После успешного `onSave` сервер возвращает канонический snapshot. UI принимает
его как новую исходную версию. При повторном открытии или перезагрузке значения
восстанавливаются только с backend, а не из браузерного кеша.

При ошибке сохранения локальные изменения остаются на экране. Пользователь видит
понятное сообщение, а соответствующее поле получает ошибку. Частичное сохранение
запрещено.

## Состояния ошибок

- `401`: авторизация отсутствует или истекла; предложить переподключение.
- `403`: текущий пользователь не администратор; показать read-denied экран без
  формы.
- `404`: связанный пользователь/группа больше не принадлежит аккаунту; обновить
  снимок и показать конфликт.
- `409`: нарушение членства, руководителя, версии или занятая группа; ничего не
  сохранять.
- `429`: сохранить введённые значения, показать просьбу повторить позже и
  учитывать `Retry-After`.

Секреты OAuth, токены и внутренние диагностические данные в браузер не
передаются и в логи не записываются.

## Manifest и упаковка

`widget/manifest.json` содержит только фактически используемые locations и
поддерживаемые amoCRM settings. Manifest, callbacks и ресурсы проверяются как
единый загружаемый пакет. Рабочий экран не получает ссылки или кнопки редактора
настроек.

## Тестирование

Backend:

- admin success и employee/manager denial;
- snapshot account isolation;
- tracked user без группы;
- второе активное membership;
- руководитель другого аккаунта/неактивный руководитель;
- одинаковые названия групп в разных аккаунтах;
- атомарный rollback при любой ошибке;
- идемпотентное повторное сохранение;
- сохранение истории при отключении пользователя/группы;
- структурированные `401/403/404/409/429`.

Frontend/widget:

- `init` не монтирует settings UI;
- `advancedSettings` показывает ровно две вкладки;
- поиск и amoCRM-группировка пользователей;
- обязательная группа для tracked user;
- независимость `hide_widget` и `track_time`;
- единый `onSave` собирает обе вкладки;
- field errors и сохранение несохранённого состояния после ошибки;
- восстановление canonical snapshot после повторного открытия.

Browser smoke:

- настройки открываются внутри контейнера amoCRM;
- нативная кнопка сохраняет обе вкладки;
- редактор отсутствует в рабочем `init`;
- собранный widget package содержит manifest, script, CSS, i18n и settings assets.

## Границы фазы

Фаза 3 не реализует автомат рабочих статусов и overlay фазы 4, ingestion событий
фазы 5, мониторинг фазы 6 или отчёты фазы 7. Она создаёт только надёжный контур
административных настроек, который эти фазы будут использовать.
