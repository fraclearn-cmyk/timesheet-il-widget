# Фаза 5: события amoCRM и интервалы активности — дизайн

**Дата:** 2026-09-23  
**Статус:** утверждённый в диалоге дизайн, ожидает проверки письменной версии  
**Основание:** `Plan.md`, результаты фазы 0 и решения пользователя от 2026-09-23

## Цель

Backend с задержкой не более одной минуты получает доступные события amoCRM, безопасно связывает их с аккаунтом, сотрудником и рабочей сессией и строит интервалы активности без выдуманной длительности. Действия мыши и клавиатуры показывают только присутствие и не становятся подтверждённой работой без CRM-события.

Фаза считается локально готовой, когда повторная доставка не создаёт дубликаты, неизвестные или неполные данные не становятся зелёной активностью, простой более пяти минут закрывает нейтральный интервал, а события во время перерыва или после завершения дня не учитываются как рабочая активность.

## Подтверждённые ограничения amoCRM

- Авторитетный источник событий — `GET /api/v4/events`. Официальный API поддерживает `filter[created_at]`, страницы до 100 записей и ссылку `next`.
- В controlled live spike фазы 0 подтверждены только семь типов и одна страница; реализация не предполагает, что это полный каталог или гарантия доставки.
- Официальные webhooks поддерживают ограниченный набор действий и не документируют подпись запроса. Поэтому webhook не является доказательством активности.
- Официальный calls API описывает добавление звонков. Read-only `GET /api/v4/calls` в тестовом аккаунте вернул `405`; универсальный источник истории звонков не подтверждён.
- Системный или неизвестный автор (`created_by <= 0`) не подменяется текущим пользователем.

## Выбранная архитектура

Используется гибридная схема:

1. Авторитетный серверный опрос каждого активного OAuth-аккаунта выполняется не реже одного раза в 60 секунд.
2. Webhook служит только ограниченным по частоте сигналом выполнить тот же опрос раньше.
3. Payload webhook не создаёт `CrmEvent`, `CallEvent` или `ActivityInterval` напрямую.
4. При потере webhook очередной опрос восстанавливает данные.
5. При отсутствии публичного webhook URL система полноценно работает в polling-only режиме.

Backend worker запускается вместе с приложением, но координируется через lease в PostgreSQL. Одновременно один аккаунт опрашивает только один процесс, даже при нескольких workers. URL сервера не зашивается в код: после переноса используется конфигурация инфраструктуры заказчика.

## Компоненты

### `AmoCRMEventClient`

- Использует существующее server-side OAuth-хранилище и доверенный tenant origin.
- Читает `GET /api/v4/events?filter[created_at][from]=...&page=...&limit=100`.
- Следует только проверенной `next`-ссылке того же tenant и ожидаемого API path.
- На `401` один раз выполняет существующую безопасную refresh rotation и повторяет запрос.
- На `429` соблюдает ограниченный `Retry-After`; временные ошибки получают bounded exponential backoff.

### `EventIngestionService`

- Берёт lease аккаунта, читает страницы, сохраняет raw envelope и нормализованную запись в одной транзакции страницы.
- Сдвигает курсор только после успешной фиксации всей страницы.
- Повтор страницы безопасен благодаря уникальному dedup key.
- Ошибка отдельного payload сохраняется как `incomplete_event`, если envelope валиден; техническая ошибка транзакции оставляет курсор на прежнем месте.

### `EventNormalizer`

- Периодически читает официальный `GET /api/v4/events/types` и хранит account-scoped snapshot каталога; встроенный минимальный словарь нужен только до первого успешного чтения. Сам известный тип не считается достаточным доказательством.
- Сохраняет исходный тип отдельно; неизвестный тип нормализуется в `unknown`.
- Подтверждённая запись требует положительные account/entity/author IDs, допустимое UTC-время, синхронизированного автора того же аккаунта и проверенную entity URL.
- Неизвестный, системный, malformed или неполный payload остаётся диагностическим и не создаёт подтверждённый интервал.

### `CallNormalizer`

- Принимает только payload от отдельно подтверждённого источника звонков.
- Подтверждение требует внешнего ID, автора, направления, фактической неотрицательной длительности, времени и связанной сущности.
- До live-подтверждения такого источника payload сохраняется как `unknown_call`/`incomplete_event`; направление и длительность не угадываются.

### `ActivityIntervalService`

- Ищет рабочую сессию того же аккаунта и пользователя на момент события.
- Подтверждённая активность возможна только внутри отрезка статуса `WORKING`.
- События в `BREAK`, `FINISHED` или вне рабочей сессии сохраняются, но не включаются в activity.
- CRM-событие без собственной длительности создаёт точку (`started_at == ended_at`, `duration_source=point`).
- Зелёный интервал с длиной создаётся только при проверенных начале/конце либо фактической длительности звонка.
- Интервал не пересекает переход в перерыв, завершение дня или границу другой рабочей сессии.

### `activity-tracker.js`

- Работает при `track_time=true`, в том числе при `hide_widget=true`, но не показывает UI.
- Наблюдает только факт разрешённых событий присутствия и `visibilitychange`; не сохраняет клавиши, текст, координаты, DOM-значения или содержимое карточек.
- Отправляет авторизованный пакет не чаще раза в минуту: UUID пакета, начало окна, UTC-время последнего действия и агрегированный счётчик.
- Не передаёт browser account/user IDs как authority; backend использует verified request context.
- Сбой backend не блокирует amoCRM, не показывает ложный статус и не копит неограниченную очередь.

## Модель данных

### `IngestionCursor`

- `account_id` — primary/account scope;
- `last_created_at`, `last_event_id` — устойчивый watermark;
- `next_poll_at`, `last_success_at`, `failure_count`;
- `lease_owner`, `lease_until` — защита нескольких workers;
- timestamps в UTC.

Опрос использует небольшой overlap относительно watermark, а дедупликация удаляет повторы. Это защищает события с одинаковым `created_at` и задержанную видимость страницы.

### `RawIngestionEvent`

- `account_id`, `source`, `external_id`, `occurred_at`;
- `dedup_key` — SHA-256 от канонических account/source/id/time, а при отсутствии ID — от канонизированного payload;
- `payload`, `received_at`, `expires_at`, `normalization_status`, безопасный `error_code`;
- уникальность `(account_id, source, dedup_key)`.

Raw payload хранится 30 дней. Ежедневная очистка удаляет только истёкшие raw envelopes; нормализованные события, интервалы и курсоры остаются.

### Нормализованные модели

- `CrmEvent` сохраняет существующий `external_id`, добавляет `original_event_type`, нормализованный `event_type`, автора, объект, время и completeness; raw payload переносится в envelope.
- `CallEvent` получает account-scoped uniqueness и completeness/source fields.
- `ActivityInterval.duration_source` принимает `point`, `observed` и `calculated`. `calculated` разрешён только при явном и тестируемом правиле, а не как значение по умолчанию для CRM-события.
- `PresenceBatch` хранит UUID пакета либо отдельную компактную idempotency-запись; отдельные клики/клавиши строками не сохраняются.

Миграция продолжает цепочку после `011`, сохраняет существующие данные и останавливает downgrade, если он уничтожил бы новые ingestion-данные.

## Дедупликация и курсор

- Основной ключ CRM-события: account + source + external ID + occurred_at.
- Повтор webhook, overlap polling и повтор страницы приводят к той же записи.
- События с одинаковой секундой сортируются устойчиво по `created_at`, затем `id`; watermark хранит оба значения.
- Cursor не продвигается через необработанную страницу.
- Конкурентная вставка разрешается уникальным ограничением PostgreSQL, а не только предварительным `SELECT`.

## Нейтральные интервалы присутствия

- Первый сигнал открывает или продолжает `unconfirmed_input` внутри подтверждённого `WORKING`.
- Следующий пакет объединяется с интервалом, только если разрыв между последними действиями не превышает 5 минут и рабочая сессия та же.
- После 5 минут без действий интервал закрывается временем последнего действия; пять минут ожидания не начисляются.
- Новый сигнал после такого разрыва открывает новый интервал.
- Переход в `BREAK`/`FINISHED` закрывает незавершённый нейтральный интервал не позднее времени перехода.
- Поздний пакет не может расширить интервал за границы подтверждённого `WORKING`.

## API

- `POST /api/v1/webhooks/amocrm/{hook_id}` — быстрый недоверенный trigger; проверяет формат/размер, сопоставляет непрогнозируемый hook ID, rate limits и ставит аккаунту ранний `next_poll_at`. Ответ не зависит от результатов polling.
- `POST /api/v1/activity/presence` — authenticated endpoint для агрегированного пакета присутствия, строгая JSON-схема без extra fields.
- Внутренний worker вызывает ingestion service; ручной admin-only trigger допускается только для диагностики и использует тот же service/lease.
- Настройка webhook выполняется server-side через официальный API только после задания публичного HTTPS base URL. Администраторская операция идемпотентно сверяет destination/settings; отсутствие настройки не отключает polling.

## Ошибки и наблюдаемость

- Пользовательские ошибки формулируются по-русски без stack trace.
- Логи содержат request/correlation ID, безопасные account/user IDs, source, page, status и стабильный error code.
- OAuth tokens, hook ID, raw payload, персональные поля и browser input в логи не попадают.
- `401` приводит к одной refresh-попытке; повторный `401` останавливает аккаунт до восстановления OAuth.
- `402` и ошибки прав не повторяются бесконечно и видны как account-level ingestion state.
- `429` и `5xx` используют bounded backoff; успешный опрос сбрасывает failure count.
- Неуспех ingestion не меняет рабочий статус, не создаёт подтверждённую активность и не блокирует интерфейс amoCRM.

## Тестирование

### Unit

- полный известный словарь и `unknown`;
- malformed/system/foreign-account author;
- call с/без проверенных полей;
- точки CRM, фактическая длительность звонка;
- пяти­минутная граница, ночная смена, break/finished boundaries;
- canonical dedup hash и raw expiry.

### Integration/PostgreSQL

- повтор страницы и конкурентная вставка дают одну запись;
- ошибка до commit не сдвигает cursor;
- lease исключает второй worker;
- OAuth refresh, 429/backoff и trusted next URL;
- migration clean/populated upgrade-downgrade-upgrade;
- cleanup удаляет raw старше 30 дней и сохраняет normalized rows.

### Browser

- tracker не отправляет клавиши, текст, координаты или browser identity;
- batching не чаще минуты, UUID повторяется после потерянного ответа;
- hidden user отслеживается без UI;
- break/finished/server outage не создают ложную активность и не блокируют amoCRM.

## Не входит в фазу 5

- Экран мониторинга, семидневная шкала и tooltip — фаза 6.
- Табель и Excel — фаза 7.
- Production scheduler tuning, monitoring dashboards и нагрузочное тестирование — фаза 8.
- Полная live-приёмка установленного `widget.zip` — фаза 9 по решению пользователя.
- Звонки не становятся подтверждёнными до появления и live-проверки источника с фактическими полями.

## Критерии готовности

1. Опрос не теряет события при повторе, одинаковом timestamp и временной ошибке.
2. Webhook только ускоряет polling и не может начислить активность.
3. Raw payload автоматически удаляется через 30 дней.
4. Unknown/incomplete/foreign/system events не создают подтверждённый интервал.
5. Подтверждённая активность находится только внутри `WORKING`.
6. CRM-события без длительности отображаются точками; длительность не выдумывается.
7. Нейтральный интервал закрывается после пяти минут тишины временем последнего действия.
8. Клиент не сохраняет и не отправляет содержимое пользовательского ввода.
9. Локальные unit, integration, browser, migration и package gates проходят; live amoCRM gate остаётся явно отложенным.
