# 1. ИСТОЧНИКИ, КОТОРЫЕ НУЖНО ИЗУЧИТЬ

Перед изменением кода обязательно изучи:

1. весь текущий ZIP-проект;
2. всю документацию внутри ZIP;
3. существующий frontend;
4. существующий backend;
5. существующие API;
6. модели базы данных;
7. существующую систему `WorkSession`;
8. существующие переходы статусов;
9. существующую систему CRM Activity;
10. текущий механизм overlay/blocking;
11. все существующие frontend-компоненты;
12. Word-документ «Табель IL» со скриншотами;
13. существующие тесты, если они есть.

В Word-документе определены три визуальные концепции:

- **Скриншот 1** — внешний интерфейс сотрудника;
- **Скриншот 2** — интерфейс просмотра активности в realtime с учётом прав;
- **Скриншот 3** — расширенный интерфейс РОП/Администратора.

Это не нужно заменять произвольным новым дизайном. Необходимо сохранить визуальную концепцию макетов и встроить новую бизнес-логику.

Исходный документ также требует блокировать работу с контактами, компаниями, сделками и задачами при статусах `Перерыв` и `Завершил(а)` и ограничивать видимость данных по правам пользователя.

# 2. ЦЕЛЬ

Доработать существующий виджет «Табель IL» для amoCRM.

Виджет должен одновременно решать две задачи:

### Личный табель

Обычный сотрудник управляет только своим рабочим временем:

- начало рабочего дня;
- перерыв;
- продолжение работы;
- завершение рабочего дня;
- повторный запуск, если это разрешено администратором;
- блокировка amoCRM во время перерыва/после завершения;
- отображение текущих итогов рабочего дня.

### Командный табель

РОП и Администратор получают:

- список сотрудников;
- текущие статусы;
- realtime-мониторинг;
- CRM activity timeline;
- детализацию активности;
- фильтрацию;
- историю;
- статистику;
- графики;
- отчёты;
- Excel.

# 3. РОЛИ И RBAC

## Обычный сотрудник

Может:

- видеть только себя;
- видеть текущий день;
- видеть свой текущий статус;
- начать рабочий день;
- перейти в перерыв;
- продолжить работу;
- завершить рабочий день;
- после завершения видеть итог текущего дня;
- повторно начать рабочий день, если это разрешено администратором.

Не может:

- видеть других сотрудников;
- видеть список подразделений;
- использовать фильтр отдела;
- использовать фильтр статуса;
- видеть командный timeline;
- видеть историю других сотрудников;
- видеть командный отчёт;
- выгружать Excel.

---

## РОП

РОП — это конкретный пользователь, которому администратор выдал соответствующие права.

РОП может:

- видеть сотрудников разрешённых ему подразделений;
- видеть realtime-статусы;
- использовать поиск;
- использовать фильтр подразделения;
- использовать фильтр статуса;
- использовать фильтр Online;
- видеть CRM activity timeline сотрудников;
- раскрывать timeline;
- видеть историю активности;
- использовать отчёт;
- использовать Excel;
- настраивать свои KPI;
- настраивать свой график.

РОП НЕ может:

- видеть сотрудников запрещённых подразделений;
- видеть детальную CRM-активность самого себя;
- менять статус другого сотрудника;
- принудительно завершать рабочий день другого сотрудника;
- управлять настройками других РОПов.

РОП видит только подразделения, которые ему назначил администратор.

Если назначено несколько подразделений — фильтр `Любой отдел` содержит только эти подразделения.

---

## Администратор

Администратор имеет полный доступ:

- все подразделения;
- все сотрудники;
- realtime;
- timeline;
- история;
- отчёты;
- Excel;
- настройки подразделений;
- настройки графиков;
- настройки РОПов;
- разрешение повторного запуска рабочего дня;
- принудительное завершение рабочего дня сотрудника.

Администратор также может видеть/настраивать расширенный интерфейс.

---

# 4. КРИТИЧЕСКОЕ ПРАВИЛО БЕЗОПАСНОСТИ

RBAC должен реализовываться **на backend/API**, а не только через скрытие элементов frontend.

Нельзя делать:

```javascript
if (isManager) {
    showAllDepartments();
}
```

и считать это защитой.

API должен проверять:

- пользователя;
- роль;
- разрешённые подразделения;
- разрешённых сотрудников;
- доступный период;
- доступ к активности.

Даже если пользователь вручную вызовет API, он не должен получить данные, на которые у него нет прав.

# 5. ЛИЧНЫЙ ИНТЕРФЕЙС СОТРУДНИКА

Визуально использовать концепцию **Скриншота 1 из Word-документа**.

Текущие кнопки и существующий механизм widget/overlay нужно встроить в интерфейс amoCRM, а не создавать отдельное самостоятельное приложение.

# 6. СОСТОЯНИЯ СОТРУДНИКА

Использовать только три рабочих статуса:

```text
Работаю
Перерыв
Завершил(а)
```

Не создавать дополнительные пользовательские рабочие статусы без необходимости.

# 7. НАЧАЛО РАБОЧЕГО ДНЯ

Когда сотрудник открывает amoCRM, виджет проверяет его состояние.

Администратор задаёт:

- начало рабочего дня;
- конец рабочего дня;

для каждого подразделения.

Например:

```text
Отдел продаж
09:00 — 18:00
```

---

## Если сотрудник открыл amoCRM ДО начала рабочего дня

Показать fullscreen overlay:

```text
Начните рабочий день

[ НАЧАТЬ РАБОЧИЙ ДЕНЬ ]
```

Не показывать сообщение «Вы опоздали».

---

## Если сотрудник открыл amoCRM ПОСЛЕ начала рабочего дня

Показать:

```text
Вы опоздали на работу

Укажите причину

[ текстовое поле ]

[ НАЧАТЬ РАБОЧИЙ ДЕНЬ ]
```

Причина обязательна только при фактическом опоздании.

После заполнения причины пользователь может начать рабочий день.

Причина опоздания должна сохраняться в данных рабочего дня.

Также необходимо сохранить количество минут опоздания.

---

# 8. КНОПКА «НАЧАТЬ РАБОЧИЙ ДЕНЬ»

Название кнопки строго:

```text
НАЧАТЬ РАБОЧИЙ ДЕНЬ
```

После нажатия:

1. создать/открыть рабочую сессию;
2. установить статус `Работаю`;
3. зафиксировать timestamp;
4. сохранить информацию об опоздании, если оно было;
5. закрыть overlay;
6. разблокировать amoCRM;
7. запустить отслеживание активности.

Никакого дополнительного подтверждения после успешного запуска не требуется.

---

# 9. СОСТОЯНИЕ «РАБОТАЮ»

Показывать:

```text
Рабочее время: HH:MM:SS
Перерыв:       HH:MM:SS

[ Перерыв ]
[ Завершить ]
```

Оба показателя должны отображаться одновременно.

`Рабочее время` — чистое время работы без перерывов.

`Перерыв` — суммарное время текущего рабочего дня, проведённое на перерывах.

---

# 10. КНОПКА «ПЕРЕРЫВ»

При нажатии:

1. немедленно зафиксировать timestamp;
2. закрыть рабочий интервал;
3. создать начало интервала перерыва;
4. изменить статус на `Перерыв`;
5. заблокировать amoCRM;
6. запустить таймер текущего перерыва.

Никакого дополнительного подтверждения.

---

# 11. INTERFACE ПЕРЕРЫВА

Использовать концепцию текущего проекта/документации.

Показывать большой overlay:

```text
Перерыв

00:15:23

[ Продолжить ]
[ Завершить день ]
```

Таймер показывает продолжительность текущего перерыва.

---

# 12. КНОПКА «ПРОДОЛЖИТЬ»

При нажатии:

1. зафиксировать конец текущего перерыва;
2. создать новый рабочий интервал;
3. изменить статус на `Работаю`;
4. разблокировать amoCRM;
5. продолжить отслеживание CRM activity.

---

# 13. КНОПКА «ЗАВЕРШИТЬ»

При нажатии в состоянии `Работаю` обязательно показать:

```text
Завершить рабочий день?

[ Отмена ] [ Завершить ]
```

Только после подтверждения:

1. закрыть текущий рабочий интервал;
2. закрыть рабочую сессию;
3. установить статус `Завершил(а)`;
4. зафиксировать timestamp;
5. остановить рабочий таймер;
6. заблокировать amoCRM.

---

# 14. ЗАВЕРШЕНИЕ ВО ВРЕМЯ ПЕРЕРЫВА

Если сотрудник находится в состоянии `Перерыв` и нажимает:

```text
Завершить день
```

показать подтверждение.

После подтверждения:

1. автоматически завершить текущий интервал перерыва текущим временем;
2. закрыть рабочую сессию;
3. установить `Завершил(а)`;
4. сохранить все интервалы;
5. заблокировать amoCRM.

---

# 15. ЭКРАН ПОСЛЕ ЗАВЕРШЕНИЯ

Показывать:

```text
Рабочий день завершён

Сегодня:

Работа      07:42
Перерывы    00:51

[ НАЧАТЬ ]
```

Обычный сотрудник видит итог текущего дня, но не получает историю за прошлые дни.

---

# 16. ПОВТОРНЫЙ ЗАПУСК В ТОТ ЖЕ ДЕНЬ

Например:

```text
09:00 — начал
13:00 — завершил
15:00 — хочет начать снова
```

Повторный запуск разрешён **только если администратор разрешил его для данного сотрудника/подразделения согласно настройкам проекта**.

Если разрешён:

```text
[ НАЧАТЬ ]
```

создаёт новую рабочую сессию.

Не объединять разные рабочие сессии в одну.

Отчёт должен корректно учитывать несколько сессий за один календарный день.

---

# 17. БЛОКИРОВКА amoCRM

Это критический функционал.

При статусе:

```text
Перерыв
```

или:

```text
Завершил(а)
```

пользователь не должен иметь возможность работать с amoCRM.

Блокируются как минимум:

- сделки;
- контакты;
- компании;
- задачи.

Также необходимо заблокировать действия, позволяющие обходить overlay.

Нельзя ограничиваться визуальным затемнением.

Использовать и адаптировать существующий механизм блокировки из проекта.

При переходе:

```text
Перерыв → Работаю
```

amoCRM разблокируется.

---

# 18. ХРАНЕНИЕ ИНТЕРВАЛОВ

Не хранить только итоговые цифры.

Нужно хранить каждый отдельный интервал.

Пример:

```text
09:00 → 11:42 WORKING
11:42 → 12:03 BREAK
12:03 → 14:27 WORKING
14:27 → 14:51 BREAK
14:51 → 18:07 WORKING
```

Итоги рассчитывать из этих интервалов.

Это необходимо для:

- истории;
- Excel;
- корректировки;
- аудита;
- отчётов;
- нескольких сессий;
- детализации рабочего дня.

Использовать существующие модели проекта, если они уже предназначены для этой задачи.

---

# 19. ПРИНУДИТЕЛЬНОЕ ЗАВЕРШЕНИЕ АДМИНИСТРАТОРОМ

Только Администратор может принудительно завершить рабочий день другого сотрудника.

При действии обязательно показать:

```text
Завершить рабочий день сотрудника?

Причина:
[________________________]

[ Отмена ] [ Завершить ]
```

Причина обязательна.

После подтверждения:

1. завершить текущий рабочий/перерывный интервал;
2. закрыть рабочую сессию;
3. установить `Завершил(а)`;
4. сохранить причину принудительного завершения;
5. записать, какой администратор выполнил действие;
6. сохранить timestamp;
7. добавить событие в audit/history.

РОП не может выполнять это действие.

# 23. СТАТУС СОТРУДНИКА В СПИСКЕ

Показывать текущий статус:

```text
Работаю
Перерыв
Завершил(а)
```

Статус другого сотрудника нельзя редактировать через этот dropdown.

Статус изменяет сам сотрудник.

Не создавать возможность РОПу менять статус другого сотрудника.

---

# 24. ФИЛЬТР «ЛЮБОЙ ОТДЕЛ»

Для РОП:

показывать только подразделения, назначенные ему администратором.

Например:

```text
Отдел продаж
VIP-продажи
```

Если у РОПа нет доступа к маркетингу, он никогда не должен получить данные маркетинга через API.

Для Администратора:

```text
Любой отдел
```

может включать все подразделения.

---

# 25. ФИЛЬТР «ЛЮБОЙ СТАТУС»

Варианты:

```text
Любой статус
Работаю
Перерыв
Завершил(а)
```

Не добавлять дополнительные статусы без необходимости.

---

# 26. ФИЛЬТР ONLINE

`Онлайн` означает:

> сотрудник совершал действие в CRM в последние 5 минут.

То есть это не просто `Работаю`.

Например:

```text
Статус: Работаю
Online: Нет
```

возможен.

Если сотрудник не совершал отслеживаемой активности более 5 минут, он не считается Online.

---

# 27. REALTIME

Командный экран автоматически обновляется каждые:

```text
30 секунд
```

Также добавить кнопку:

```text
Обновить
```

Ручное обновление должно немедленно запрашивать актуальные данные.

Не делать frontend-only fake realtime.

---

# 28. CRM ACTIVITY

Использовать существующую систему отслеживания активности проекта.

Учитывать минимум:

- сделки;
- контакты;
- компании;
- задачи;
- звонки;
- заметки;
- другие существующие события, которые уже поддерживает проект.

Не создавать вторую независимую систему Activity Tracking.

---

# 29. TIMELINE

Для каждого сотрудника показывать горизонтальный timeline:

```text
00:00      06:00      12:00      18:00      24:00
────────────────────────────────────────────────
             ████▓▓▓████░░░
```

Зелёный цвет не использовать как единственный тип активности.

Каждый тип CRM activity должен иметь отдельный визуальный цвет.

Например:

```text
Сделки
Контакты
Компании
Задачи
Звонки
Заметки
Другое
```

Конкретные цвета выбрать в соответствии с существующим дизайном проекта/макетом. Не ломать существующую дизайн-систему.

---

# 30. ПЕРЕСЕЧЕНИЕ АКТИВНОСТИ

Если в одном временном интервале произошло несколько типов активности:

НЕ создавать несколько горизонтальных полос.

Использовать одну полосу.

При наведении/клике показывать детализацию:

```text
Активность
09:42–09:47

Сделки: 3
Контакты: 1
Задачи: 2
Звонки: 1
```

Также показывать конкретные события, если существующая модель ActivityEvent содержит соответствующие данные.

---

# 31. СТАТУС И ACTIVITY TIMELINE — РАЗНЫЕ СУЩНОСТИ

Не смешивать:

```text
Работаю
Перерыв
Завершил(а)
```

с:

```text
CRM activity
```

Например сотрудник может иметь:

```text
Статус: Работаю

CRM Activity:
последнее действие 8 минут назад
```

В таком случае:

```text
Статус = Работаю
Online = Нет
```

Это корректное состояние.

---

# 32. РАСКРЫТИЕ TIMELINE

Справа от timeline должна быть кнопка раскрытия.

При нажатии раскрывать историю:

```text
08 августа
00:00 ─────██████────────

07 августа
00:00 ───────████────────

06 августа
00:00 ─────────███──────
```

История командного activity timeline:

```text
сегодня + предыдущие 7 дней
```

То есть максимум 7 дней исторической activity timeline в этом компоненте.

# 33. DETALIZATION

При раскрытии дня пользователь должен иметь возможность получить подробности активности.

Использовать существующие данные:

- тип события;
- время;
- объект amoCRM;
- действие;
- сотрудник;
- другие данные, которые реально доступны в существующей ActivityEvent.

Не придумывать данные, которых нет в backend.

- не смешивается с причиной принудительного завершения.

# 44. KPI

В интерфейсе должны быть KPI-карточки.

Базовый набор:

```text
Сотрудников на работе
На перерыве
Завершили работу
Отработано времени
```

Дополнительно могут быть:

```text
Опоздали
Среднее рабочее время
Среднее время перерывов
```

Настройки индивидуальны для каждого РОП/Администратора.

Настройка одного пользователя не должна менять dashboard другого.
